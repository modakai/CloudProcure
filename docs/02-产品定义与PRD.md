# 02 产品定义与 PRD

版本：v1.1｜2026-10-20｜适用：个人学习与作品集。关联：[需求](03-软件需求与验收.md)、[实施计划](11-实施计划与任务拆解.md)。

## 1. 产品定位与业务假设

云采为中小企业提供办公物资采购：企业成员选品、内部审批、企业财务支付、平台仓库履约。运营方拥有统一商品和库存，企业客户是买家租户；平台不是为每家企业单独托管一家商城。

这个选择有意保留真实的 B2B 问题：人员离职后权限撤销、采购不能自批、审批后价格不能变、库存可能不足、支付状态可能未知、操作需要审计。它避开首版无法可靠完成的供应商入驻、分账、税务和授信。

目前没有真实访谈和市场数据；下述痛点是设计假设，应通过使用者验证，不能据此声称已验证商业价值。

新增明确学习目标：基于Spring Security 7开发自己的OIDC认证服务；当前只有一个采购门户客户端，买家与平台工作台是同产品的角色视图，不为展示SSO额外构造第二系统。首版本地账号登录，社交登录留待以后。业务持久化使用Spring Data JPA。

| 目标用户 | 当前假设的痛点 | 产品提供的结果 |
|---|---|---|
| 企业采购员 | 群聊申请难追踪、重复购买 | 可查询的申请、审批和订单时间线 |
| 审批人 | 审批缺少金额、用途和责任记录 | 快照化申请、禁止自批、明确审批记录 |
| 企业财务 | 不知道哪些订单可付款、退款不透明 | 待支付列表、付款结果、退款追踪 |
| 企业管理员 | 离职人员仍能看采购数据 | 成员、角色、数据范围和停用控制 |
| 平台商品运营 | 商品与价格变更影响已批准采购 | 版本化报价、订单商品快照 |
| 仓库人员 | 付款与出库状态不同步 | 已确认资金与库存的可履约清单 |

## 2. 成功定义

作品集验收不看服务数量和技术名词数量，使用以下证据：

- 新用户可在演示环境走完申请到收货，且能说明每个状态由谁确认。
- 至少两家企业、每家四类成员；任何已测试的跨租户读写均失败。
- 并发抢购不会超卖；重复下单、回调、消息和退款不会重复生效。
- 在消息服务中断、交易服务重启、支付回调丢失后可恢复，并保留过程证据。
- 报告给出环境、样本、P95、错误率和瓶颈，不写无依据的“百万并发”。

产品指标先记录基线，再决定优化目标：申请提交成功率、审批时长中位数/P95、批准后成功成单率、付款后完成履约率、库存失败率、支付未知比例、异常工单存续时长。分母排除规则与取消原因必须随报告附上。

## 3. 角色与职责

| 角色 | 允许的核心动作 | 默认数据范围 |
|---|---|---|
| 采购员 BUYER | 选品、提交、撤回未批准申请、查看自己订单、收货 | 本企业本人创建的数据 |
| 审批人 APPROVER | 查看分派任务、通过/拒绝 | 本企业分派给自己的任务 |
| 财务 FINANCE | 查看本企业待付、发起支付、申请退款 | 本企业订单及付款资料 |
| 企业管理员 TENANT_ADMIN | 成员与角色、审批人配置、查看企业采购 | 本企业；不自动获得付款权限 |
| 商品运营 CATALOG_OPERATOR | 商品、价格、上下架 | 平台商品；不可读取买家敏感资料 |
| 仓库操作员 WAREHOUSE_OPERATOR | 入库、盘点调整、发货 | 平台库存、履约必需收货信息 |
| 平台支持 SUPPORT | 查询异常流程，受控处理补偿 | 经授权的指定企业/工单 |
| 身份管理员 IDENTITY_ADMIN | 受控账号创建、全局停用、密码重置与认证运维 | 全局身份；不自动获得企业采购或资金权限 |

同一账号可加入多企业，但每次请求只能有一个有效企业上下文。平台员工与买家成员使用不同授权范围；平台员工不是“把 tenant_id 改成 0 就能看全部”的特殊买家。

## 4. 版本范围

| 范围 | 必须完成 | 明确暂缓 |
|---|---|---|
| MVP 核心 | 登录、两租户隔离、成员角色、商品、申请、单级审批、锁库存、模拟支付、发货、收货、审计 | 优惠券、积分、搜索引擎、推荐 |
| 实战增强 | 超时取消、幂等、Outbox/Inbox、发货前退款、对账、限流、链路、恢复演练 | 实物退货、部分退款、拆单拆包 |
| 进阶实验 | Seata 对照实验、容器多副本、灰度、容量分析 | 直接接入真实资金、多商户分账 |
| 未来生产立项 | 真实身份与支付渠道、法规评估、SLA、容量与安全审计 | 不以本设计文档替代采购/合规评审 |

业务固定：CNY、整数量商品、每单最多50行、每行1～999件、金额总计不超过100万元。单价含税；MVP运费为0，不计算优惠和税额拆分。真实税务开票另立项。

## 5. 关键用户旅程

1. 管理员创建企业、邀请成员、设置一个有效审批人；邀请失效和重复成员均有提示。
2. 采购员查商品，添加采购清单，填写用途和收货地址。前端显示参考库存，提交时服务器重新校验价格与可售状态。
3. 提交后冻结商品名称、规格、单价、数量、总价、地址和审批人。审批有效期24小时；期间不占库存。
4. 审批人查看明细与用途，通过或拒绝并记录意见；创建人不能审批自己的申请。批准后异步尝试成单并锁库存。
5. 缺货、商品禁售或技术异常分别显示“缺货无法成单”“商品不可售”“处理中”；技术未知不能伪装缺货。修改后重新申请，不让用户误以为原审批继续有效。
6. 锁库成功进入待支付，默认30分钟。财务付款中只能查询，不能因为网络超时重复创建新付款。
7. 付款确认且库存预占转为已分配后，仓库可发货。采购员确认收货后完成。
8. 发货前财务可申请整单退款；系统先冻结履约，再退款、释放库存。退款中持续显示进度；发货后首版转人工支持，禁止自动假退货。

## 6. 页面与交互需求

| 页面 | 核心内容与动作 | 必须设计的异常态 |
|---|---|---|
| 登录/企业切换 | 自建identity登录页、OIDC回调、当前企业、角色提示 | 凭据错误、限速、账号停用、无企业、企业停用、会话过期、无权切换 |
| 账号初始化/密码修改 | 受控邀请激活、一次性设置密码、当前密码校验、退出 | 邀请过期/重放、弱密码、重置后旧刷新凭据不可用 |
| 商品列表/详情 | 分类、关键词、价格、规格、可售状态 | 空列表、下架、库存仅参考、加载失败 |
| 采购申请编辑 | 商品行、用途、地址、金额合计 | 非法数量、超限、价格变化、重复提交 |
| 我的申请/详情 | 状态、审批记录、成单结果 | 拒绝理由、申请过期、正在成单、缺货 |
| 待审批/详情 | 申请快照、通过、拒绝 | 不能自批、已被处理、审批人失效 |
| 企业订单/详情 | 金额、付款倒计时、状态时间线 | 支付未知、取消中、退款中、异常工单 |
| 财务工作台 | 待付、支付记录、退款记录 | 重复付款、状态待核查、渠道失败 |
| 组织管理 | 成员、角色、审批人 | 最后管理员不可停用、审批人离职 |
| 商品/库存管理 | 上下架、调价、入库、调整理由 | 负库存、并发冲突、重复单据 |
| 履约工作台 | 可发货列表、物流单号、发货确认 | 退款冻结、重复发货、库存未确认 |
| 运营异常工作台 | 失败原因、重试记录、对账差异 | 无权限、正在处理、结果未知 |

按钮禁用只能减少误操作；权限、状态和重复提交必须由后端兜底。对“处理中”展示最后更新时间和查询入口，不给出未经确认的成功提示。金额展示两位小数但接口使用整数分。

支持键盘操作、表单标签、可读错误提示，状态不用颜色单独表达；提交后保留用户输入。首版桌面Web，窄屏可阅读，暂不做原生App。

## 7. 业务参数与运营约定

审批有效期24小时；支付窗口30分钟；支付在途先查明结果再取消；库存不依赖 Redis TTL 自动释放。参数在新流程启动时快照，调整不追溯修改旧订单。

下架阻止新申请和新成单；已经创建并锁库的订单按快照履约。涉及安全召回时走专项冻结，不能只靠“下架”代替召回。历史记录不可因商品删除而丢失。

通知MVP仅站内时间线和待办；短信、邮件和即时通讯推送不列入核心成功条件。列表统计允许秒级延迟，详情写后读取主数据。

## 8. 可演示的故事与验收材料

准备企业A、B；每家采购员、审批人、财务、管理员；平台商品运营和仓库人员；三个商品分别为库存充足、仅剩一件、已下架。

演示至少包括：正常收货、审批拒绝、不能自批、两人抢最后一件、重复付款回调、支付成功但交易服务宕机、退款与发货竞争、篡改企业ID被拒绝。每个故事附角色、请求、状态变化、审计记录和对应测试编号。
