# 06 接口与事件契约

版本：v1.1｜本文件为契约设计清单，不是已发布OpenAPI。M0/M1实施时生成并校验机器可读Schema，不能把下表当成接口已经可调用。

## 1. 协议与公共约束

外部REST前缀`/api/v1`，JSON UTF-8。网关BFF采用服务端会话；内部服务独立校验可信Token和服务身份。企业选择可以用`X-Tenant-Id`表达，但它只是选择值，必须与已验证身份和有效成员资格匹配。平台接口固定走平台权限路径。

OIDC端点由identity-service中的框架提供，授权码回调由Gateway OAuth2 Client处理，不包含在普通JSON CRUD协议内。登录页、授权、Token、发现/JWKS、退出与账号接口详见[认证设计](13-自建OIDC认证服务设计.md)。ID Token不可用于业务API；服务身份Token不可充当用户Token。JWT注销与账号停用的区别按该文执行。

写接口要求`Idempotency-Key`（随机高熵、最大128字符），服务以租户/平台作用域、操作者、操作名和键联合去重，并比较规范化请求哈希。不可用另一个用户的结果作为缓存响应。记录须与业务效果同事务或绑定永久业务唯一键；处理中重试返回同一operationId。

创建同步资源返回201及Location；异步操作202与operationId、当前状态、查询路径；成功读200；同步无返回写204。400参数非法，401身份无效，403权限不足，404不存在或不应泄露的跨租户资源，409状态/版本/幂等冲突，429限流，503依赖不可用。客户端不能仅凭HTTP202显示业务完成。

错误采用`application/problem+json`风格：type、title、status、detail、instance，并扩展code、traceId、violations。错误不含SQL、堆栈、密钥或其他企业资源标识。参考[Problem Details RFC 9457](https://www.rfc-editor.org/rfc/rfc9457)。

成功响应由接口选择业务DTO或可选`Result<T>`（code、message、data；默认成功code为`OK`），不进行全局自动包装，不改变201/202/204等HTTP语义。错误仍只使用Problem Details，不自动转为Result。公共错误码采用`INVALID_REQUEST`、`VALIDATION_FAILED`、`UNAUTHENTICATED`、`FORBIDDEN`、`NOT_FOUND`、`CONFLICT`、`TOO_MANY_REQUESTS`、`DEPENDENCY_UNAVAILABLE`等稳定字符串；业务错误码在所属服务实现`ErrorCode`。`violations`为`{field,message}`数组，无字段违例时为空，不携带被拒绝的原始值；`instance`仅含路径，不含查询参数。完整公共码见`CommonErrorCode`。

错误响应和本服务生成的`X-Trace-Id`头使用同一标识；优先取Micrometer当前span，没有span则生成当前请求的关联标识。不直接采信客户端`X-Trace-Id`；本地回退标识不代表分布式追踪已实现。MVC和WebFlux分别适配安全链与异常入口，资源服务器保留Bearer挑战头及协议状态码。OAuth/OIDC专用链沿用协议处理器，不接入业务错误处理器。

金额字段`amountMinor`为整数分，`currency`固定CNY；大整数ID以字符串传输；版本`expectedVersion`用于审批、发货和角色等并发敏感修改。列表返回items、nextCursor、hasMore，不默认每次全表COUNT。

公共`CursorRequest`仅包含cursor和limit：limit默认20、范围1～100，cursor最长2048字符；Controller需使用`@Valid`。游标内容、租户绑定和查询条件有效性由各服务校验。末页`nextCursor=null、hasMore=false`，存在下一页时必须给出非空游标。

## 2. 外部API清单

表中路径均加`/api/v1`。BFF认证回调按框架安全配置另设路径，不手写Token登录接口。

| 方法与路径 | 角色/归属 | 输入要点 | 返回与规则 |
|---|---|---|---|
| GET /me | 已登录 | 无 | 身份、可用企业、当前角色，不返回密钥 |
| POST /session/tenant | 有效成员 | tenantId | 切换会话企业，防CSRF并重校成员 |
| POST /platform/tenants | 受控平台管理 | 企业资料 | 201，审计；不开放匿名注册企业 |
| GET/POST /tenants/current/members | 企业管理员 | 分页或邀请身份 | 仅当前企业；创建幂等 |
| PATCH /tenants/current/members/{id} | 企业管理员 | status、roles、expectedVersion | 禁止移除最后有效管理员；即时写权限撤销 |
| PUT /tenants/current/approval-setting | 企业管理员 | approver、expectedVersion | 不允许失效成员 |
| GET /catalog/skus | 成员 | keyword、category、cursor | 平台可售商品 |
| GET /catalog/skus/{id} | 成员 | id | 当前价与版本，库存仅参考 |
| POST/PATCH /platform/skus | 商品运营 | SKU及版本 | 价格和状态变更审计 |
| POST /requisitions | 采购员 | 商品行、用途、地址 | 201草稿，不信任客户端金额 |
| PATCH /requisitions/{id} | 草稿创建人 | 明细、expectedVersion | 只允许DRAFT |
| POST /requisitions/{id}/submit | 草稿创建人 | expectedVersion | 200 PENDING，冻结报价与审批人 |
| POST /requisitions/{id}/withdraw | 创建人 | expectedVersion | 仅PENDING，不能撤回已批准申请 |
| GET /requisitions | 采购员/管理员 | scope、state、cursor | 服务端限制本人/本企业范围 |
| GET /approval-tasks | 审批人 | cursor | 分派给本人 |
| POST /approval-tasks/{id}/decision | 指定审批人 | APPROVE/REJECT、reason、expectedVersion | 通过返回202成单处理中，拒绝200 |
| POST /approval-tasks/{id}/reassign | 本企业管理员 | newAssignee、reason、expectedVersion | 仅待审批且原审批人失效；新成员有效、具审批权且非申请人；保留历史，不延长原有效期 |
| GET /orders | 本人/财务/管理员 | state、cursor | 按角色限制，不仅靠菜单 |
| GET /orders/{id} | 本企业获权者 | id | 权威状态、快照、时间线 |
| POST /orders/{id}/payment-intents | 财务 | expectedVersion | 202；trade建立付款栅栏后异步交付payment |
| POST /orders/{id}/cancel | 获授权采购/财务 | reason、expectedVersion | 202；在途付款必须核验，不立即承诺取消 |
| POST /orders/{id}/refunds | 财务 | reason、expectedVersion | 202；先冻结履约，仅整单 |
| POST /orders/{id}/receipt | 创建人或授权收货角色 | expectedVersion | 仅SHIPPED可确认 |
| GET /payment-intents/{id} | 本企业财务 | id | 支付状态及查询时间，不含回调密钥 |
| GET /refunds/{id} | 本企业财务 | id | 退款最终/在途状态 |
| POST /platform/stock-receipts | 仓库 | SKU、数量、单据号、原因 | 201，单据幂等 |
| POST /platform/stock-adjustments | 仓库主管权限 | 目标调整、原因、expectedVersion | 严格校验可用量与审计 |
| GET /platform/fulfillments | 仓库 | state、cursor | 仅作业必需个人信息 |
| POST /platform/fulfillments/{id}/ship | 仓库 | carrier、trackingNo、expectedVersion | 仅READY原子改SHIPPED |
| GET /operations/{id} | 同企业且有原操作权限 | id | 编排状态、最后更新、允许重试动作 |
| GET /platform/exceptions | 受控支持 | ticket、scope | 资金/库存差异与责任人 |
| POST /platform/exceptions/{id}/retry | 专项权限 | reason、expectedVersion | 仅重试既有幂等任务，不任意篡改状态 |

MVP不支持GET列表直接批量导出PII。支付渠道回调为专用外部入口`/integrations/payments/{channel}/callbacks`，不要求浏览器会话，必须验证渠道签名与商户绑定，详见安全文档。

## 3. 内部契约

报价：catalog提供批量quote接口，接收SKU数量并返回名称规格、单价分、金额合计、priceVersion、报价时间和有效期。trade校验返回SKU完整性、币种与总额，提交后保存快照。报价不可用时拒绝提交。

成单可售复核：catalog提供批量检查当前SKU可售状态的内部接口，trade在批准后、发送库存预占前调用；只复核禁售，不重新计价。复核失败保留任务重试，明确禁售则不发预占并结束成单。已复核后遇普通下架仍履行该次成单承诺；安全召回另走专项冻结。

授权：access提供按subject、tenant、permission、resourceScope的决策接口。高危写实时检查；低危查询可缓存≤60秒。调用方不能把HTTP头中的任意角色声明当作决策。

渠道适配：payment定义创建支付、查询支付、关闭支付、创建退款、查询退款五个必要操作。结果必须区分SUCCESS、DEFINITIVE_FAILURE、PENDING/UNKNOWN；超时不是失败。模拟渠道用固定测试指令产生各类结果，只在开发测试环境可用。

## 4. 消息信封

每条命令/事件有：eventId（全局唯一字符串）、eventType、schemaVersion、occurredAt、producer、aggregateType、aggregateId、aggregateVersion、tenantId或platformScope、correlationId、causationId、traceparent、payload。业务字段包括orderId、commandId、reservationId、paymentId等所需关联，不带用户访问Token。

同一语义命令重发保持commandId与eventId；真正新一次支付尝试使用新的attemptNo。不要每次重试都创建一个看起来全新的业务动作。payload的企业、金额和单号必须与本地不可变快照核对。

| 命令/事件 | 生产者→消费者 | payload核心字段 | 成功后的事实/回复 |
|---|---|---|---|
| ReserveStock | trade→inventory | orderId、tenantId、items、orderVersion | StockReserved或StockRejected |
| ReleaseStock | trade→inventory | orderId、reason、releaseStage | StockReleased；可先建墓碑 |
| OpenPaymentIntent | trade→payment | orderId、amountMinor、currency、fence | PaymentIntentOpened/PaymentPending |
| ClosePaymentIntent | trade→payment | orderId、fence、reason | PaymentClosed或PaymentSucceeded/Unknown |
| PaymentSucceeded | payment→trade | orderId、paymentId、amountMinor、channelRef、paidAt | 接受付款或关闭后触发退款异常流程 |
| CommitStock | trade→inventory | orderId、paymentId | StockAllocated或异常待核查 |
| AuthorizeFulfillment | trade→fulfillment | orderId、addressSnapshot、items、orderVersion | FulfillmentReady |
| FreezeFulfillment | trade→fulfillment | orderId、refundRequestId、orderVersion | FulfillmentFrozen或AlreadyShipped |
| CreateRefund | trade→payment | orderId、paymentId、refundNo、amountMinor | RefundPending/RefundSucceeded/RefundFailed |
| CloseFulfillment | trade→fulfillment | orderId、refundNo | FulfillmentClosed |
| UnfreezeFulfillment | trade→fulfillment | orderId、refundNo、orderVersion | FulfillmentReady，仅确定退款失败时 |
| ShipmentDispatched | fulfillment→trade,inventory | orderId、shipmentId、trackingNo、shippedAt | 订单SHIPPED；库存实际出库 |
| RefundSucceeded | payment→trade | orderId、refundNo、amountMinor | 后续释放库存，完成退款编排 |

技术失败不发StockRejected冒充业务缺货；保留命令重试。命令结果可以重复发送，接收方必须幂等。

## 5. Topic、投递与演进

按环境隔离命名，例如`dev.trade.commands.v1`、`dev.inventory.events.v1`，同一服务独立消费组。部署脚本创建Topic和ACL，不开放自动任意创建。具体Topic拆分和RocketMQ消费接口在POC确定并写入机器契约。

至少一次投递；不宣称端到端Exactly Once。Outbox租约避免多发布者无界重复，Inbox和业务唯一键保证重复无副作用。尽量按orderId分组保序，但正确性必须依靠状态校验、墓碑和业务栅栏；不能把不同Topic间顺序当作保证。

aggregateVersion用于识别过期事件，不要求消费者看到生产者每一次版本递增；消费者可能只订阅部分事件。无法应用的未来事件进入等待/核对任务，查询权威状态，不直接丢弃，也不盲等不存在的连续序号。

兼容增加可选字段、保留旧含义；删除必填字段、改变金额单位或状态语义必须升schemaVersion并执行双读/迁移。未知事件版本告警并隔离，不确认成“成功处理”。毒消息隔离后原业务仍保持待处理，重放需原因、操作者、旧eventId及审计。
