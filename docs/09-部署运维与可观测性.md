# 09 部署、运维与可观测性

版本：v1.1｜已提供MySQL/Redis/Nacos开发Compose并通过静态检查；尚未启动中间件、部署集群或生成Kubernetes清单。详见[部署说明](../deploy/README.md)。

## 1. 环境与资源预算

| 环境 | 用途 | 建议形态 | 可靠性边界 |
|---|---|---|---|
| Dev最小 | 开发单用例 | IDE按需启动identity与业务服务；Compose单节点MySQL、Redis、Nacos、RocketMQ | 不保证高可用；数据可用合成种子重建 |
| Demo完整 | 作品集演示 | 六业务服务+identity+网关，共八应用；中间件单节点；观测按需 | 能复现故障，不能宣称生产HA |
| CI集成 | 验证提交 | 测试容器或短期环境，隔离库、Topic和身份 | 不连接演示或生产数据 |
| Staging候选 | 压测与发布演练 | 多副本应用、持久化数据库、与生产同类消息拓扑 | 需版本锁定和恢复报告 |
| Prod未来 | 真实业务 | 独立故障域、受管DB或验证过的HA、MQ HA、Nacos集群、TLS | 另做容量、成本、安全和业务上线评审 |

本机建议16GB内存起步、32GB更适合完整演示，SSD空闲约40GB用于镜像和数据；这是预算建议，不是已测最低配置。8GB机器可分阶段只启动本次涉及服务，观测使用简化日志。容器JVM初始限额约256～512MB/服务，中间件单独预算并测量，不能把总limit算得比宿主机内存还大。

Windows开发推荐Docker Desktop的Linux容器与WSL2；先确认可用虚拟化和资源。没有容器环境时保留远程测试环境方案，不为了演示在个人机器上手工装齐全部生产组件。

## 2. 配置、网络与启动顺序

配置清单必须包含：应用名、环境、Nacos namespace/group/Data ID、注册认证、服务端端口、数据库URL与账号引用、MQ客户端协议与地址、Topic/Group、Redis会话、OIDC issuer/audience、渠道模拟开关、超时和任务参数。

新增identity配置：固定issuer URL、门户client与精确回调/退出地址、服务client/scope、认证与业务数据库迁移、持久化签名密钥位置/kid、历史公钥保留、Token时效、身份/门户会话独立Redis命名空间、账号初始化与MFA密钥引用。issuer使用浏览器与容器都可解析的固定地址；发现文档不能一会返回localhost一会返回内部容器名。转发头只信任受控入口代理。

不同环境使用独立数据库、namespace、Topic和密钥。namespace是环境隔离，不是买家租户隔离。按固定镜像tag加digest和effective POM记录版本，禁止使用latest浮动镜像；部署前检查已知漏洞。

启动：数据库与Flyway迁移→Redis/MQ/Nacos→identity与持久化密钥加载→组织商品等基础服务→交易库存支付履约→网关→账号/成员种子核对与冒烟。identity不依赖access登录，避免认证循环；账号初始化和企业成员绑定是可重试的显式步骤。注册成功不代表readiness通过。

所有服务暴露独立管理端口且只在内部网络可达。Nacos的HTTP、gRPC及集群端口与RocketMQ的Remoting连接按冻结版本官方配置核对；禁止只开放旧教程单个端口后误判“客户端Bug”。外部仅开放HTTPS网关与专用签名回调入口。

## 3. 数据库迁移与发布

每个服务持有自己的迁移脚本和schema history，单独部署迁移任务，部署身份与运行身份分离。禁止每个应用副本同时任意改表。先加字段/表、兼容旧版本、回填验证，再切流量；删除旧字段至少跨一个验证周期。

发布门禁：构建→单测→真实MySQL约束与集成→契约→Secret/依赖/镜像扫描→制品签名/摘要→Staging迁移→冒烟→人工查看证据→部署。首版只需实现实际使用的CI平台一种，不同时维护两套流水线。

发布后验证登录、企业隔离、提交、批准、库存、付款与退款恢复。异常时先停止新流量或写操作，再根据兼容矩阵回滚应用。数据库迁移不执行盲目降级；破坏性变更要求前向修复方案与备份，不许把“回滚镜像”当作“数据也能回滚”。

滚动发布需要旧新事件Schema兼容。应用优雅关闭：停止接新请求→退出注册→停止领取任务→等待短事务和消息处理→关闭连接。租约和消息可重投保证进程强杀也能恢复。

## 4. 可观测性

| 类型 | 至少收集 | 关键注意 |
|---|---|---|
| 请求 | route、method、status、latency、error_code | route模板避免把orderId放指标标签 |
| JVM与连接池 | CPU、heap、GC、线程、活跃/等待连接 | 区分CPU瓶颈与DB连接等待 |
| 消息 | 发送失败、消费失败、积压、最老消息年龄、重投次数 | 数量低但最老消息卡住同样危险 |
| 业务流程 | 审批等待、成单时延、待付超时、支付未知、退款未知 | 未决资金年龄是优先告警项 |
| 一致性 | 待发Outbox、未推进任务、库存/支付对账差异 | 不能只看HTTP成功率 |
| 安全 | 拒绝授权、跨企业尝试、角色变更、支持授权 | 记录审计，避免泄露敏感payload |

业务单号、tenantId、eventId、traceId放日志与链路属性；不要把高基数用户/订单/企业ID直接做Prometheus标签。事件跨进程保留traceparent和correlationId；异步长流程可用新trace加link，避免一条追踪无限增长。

Demo可100%采样并关闭敏感字段；持续环境按成本采样，并保留异常证据。日志保留初始7天、指标15天、链路3天为实验预算，生产按成本、审计和隐私要求另定。

## 5. 初始告警与SLO

| 告警 | 初始阈值（待校准） | 等级与处理 |
|---|---|---|
| 金额不符/重复渠道资金/跨租户成功访问 | 任意一例 | P0，立即暂停相关写路径并核实 |
| 数据库不可用、核心服务无可用实例 | 持续1分钟 | P0，按恢复手册 |
| 服务端错误率 | 5分钟>1%，且请求样本≥100 | P1，定位依赖；低流量另用连续失败检查 |
| 付款或退款UNKNOWN | 最老>5分钟 | P1，主动查渠道，禁止强行改结果 |
| Outbox待发/编排卡住 | 最老>60秒 | P1，查MQ、消费、租约与数据库 |
| 库存异常 | 可售量负数或账实差异 | P0/P1，停止涉事SKU新交易 |
| 业务时延 | 核心异步P95>5秒持续10分钟 | P2，先看积压与连接池 |

生产候选99.9%月度可用性对应按30天计算约43.2分钟错误预算。SLI定义为合规且在延迟预算内完成的核心请求/有效请求；付款最终确认另有业务时延SLI。缺货和用户权限错误不混成系统不可用，但不能隐藏500与超时。个人单机环境只报告实际可用数据，不承诺SLA。

## 6. 备份恢复

生产候选RPO≤5分钟、RTO≤60分钟依赖连续binlog/等价PITR与独立备份，并非启用定时备份就自动满足。每日全量、持续日志、加密异地或独立故障域保存，具体保留周期评审后确定。

恢复演练：记录时间T0和数据校验点→从独立备份恢复各库及日志到约定时间→隔离所有回调和出站渠道写操作→检查状态、Outbox、Inbox、任务和租约→查询渠道事实→执行跨服务对账→确认无重复扣款和库存漂移→逐步放开流量，记录T1与实际数据缺口。

多库分别恢复可能产生时间切面差异；资金事实以渠道核验为准，库存以流水和履约事实核验，不声称多个本地事务数据库天然拥有一个全局一致快照。MQ消息不替代数据库备份；Redis缓存可重建，会话丢失要求重新登录。identity_db、加密密钥及签名密钥需分别受控备份，恢复不得直接重新信任备份中的旧刷新授权；首版恢复流程先撤销全部旧授权并清除身份/BFF会话，再重新登录。旧JWT的剩余窗口仍按认证设计处理。

## 7. 故障操作手册

| 故障 | 先做什么 | 禁止做什么 | 恢复验证 |
|---|---|---|---|
| MQ不可用 | 检查Outbox与磁盘，限量接收异步写入，积压超限拒绝新写 | 删除待发记录“清理故障” | 恢复后重发、去重、对账 |
| Nacos不可用 | 保留最后有效配置；观察实例发现；停止需要新配置的发布 | 切换空白配置、关闭认证 | 恢复注册和限流规则，重启抽样验证 |
| Redis不可用 | BFF拒绝失效会话，商品缓存回源受限 | 绕过登录或用缓存金额付款 | 会话重新登录、回源负载恢复 |
| 支付回调丢失 | 按唯一商户号主动查询 | 把超时直接记为失败/新开支付 | 渠道与payment/trade对齐 |
| 库存预占卡住 | 查trade及支付状态，触发既有关闭/释放任务 | 直接把reserved清零 | 流水、可售、预占账一致 |
| 数据库迁移失败 | 停止发布，检查迁移记录和备份，前向修复 | 未核实就重跑删表脚本 | 新旧版本兼容与冒烟 |
| 密钥泄露 | 撤销、轮换、审计影响范围 | 只删Git当前文件 | 旧凭据不可用、新凭据工作 |
| identity不可用 | 停止新登录/刷新，高危用户写失败关闭；观测现有短期Token与缓存边界 | 绕过账号状态检查、临时签发万能Token | 恢复发现/JWKS、刷新、登录与账号状态校验 |

个人演示不发送真实告警给第三方人员，先以本地看板和日志复现告警规则。
