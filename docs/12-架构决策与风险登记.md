# 12 架构决策、风险与完整性边界

版本：v1.1｜决策状态“采纳”表示设计选择，不表示实现和验证已完成。认证与持久化方案经用户确认更新。

## 1. 架构决策记录

| 编号 | 决策 | 原因与代价 | 重新评估触发条件 |
|---|---|---|---|
| ADR-001 | 采纳企业买家、多租户、自营平台 | 保留采购复杂度，减少多卖家结算；不能用于多商家市场 | 真实需要供应商入驻、报价与分账 |
| ADR-002 | 六业务服务+自建identity+网关 | 教学覆盖业务边界与认证；共八应用，增加部署排障成本 | 运维负担压过独立演进收益时，合并部署或模块化 |
| ADR-003 | 使用SCA最新正式版，补丁候选先POC | 满足学习新代际；承担生态适配成本 | 后续正式版发布、漏洞或POC失败 |
| ADR-004 | [业务Spring Data JPA，协议仓储复用框架JDBC](adr/0002-owned-oidc-and-jpa.md) | 练习ORM与显式并发控制；增加实体生命周期和查询优化要求 | 实测ORM限制导致某用例需要专用SQL，不全局重写 |
| ADR-005 | [Spring Security 7自建OIDC+BFF](adr/0002-owned-oidc-and-jpa.md) | 增加标准认证学习目标；承担账号、授权、密钥与测试责任 | 未来真实身份接入或成本超过自维护收益；当前不造第二SSO系统 |
| ADR-006 | 共享逻辑结构+tenant_id隔离买家数据 | 个人可运行；原生SQL和缓存必须逐项测试 | 合规或大客户要求独立库/密钥/恢复 |
| ADR-007 | [本地事务+Outbox/Inbox+显式补偿](adr/0001-explicit-compensation.md) | 能处理长流程与外部渠道；要写状态、对账和恢复 | 需要CDC优化时替换发布方式，不改变业务不变量 |
| ADR-008 | 不用Redis承担库存最终正确性 | 数据库条件更新和流水更容易验证；热点容量有上限 | 实测数据库成为瓶颈且有完整账实恢复设计 |
| ADR-009 | 退款先冻结履约 | 避免退款后发货；未知退款可能长时间冻结 | 增加实物退货、部分退款时重新设计 |
| ADR-010 | 无自动库存TTL释放 | 防止支付成功但库存已回卖；牺牲故障期间库存周转 | 有可证明安全的租约与支付协调机制 |
| ADR-011 | 首版单仓、单币种、整单、单级审批 | 让个人有机会完成完整闭环；业务表达有限 | 实际用例证明需要扩展，不提前抽象 |
| ADR-012 | Compose先行，K8s后置 | 把时间用在业务正确性；首版不具生产HA | 多节点演练或真实部署计划成立 |

## 2. 风险登记

| 编号 | 风险 | 概率/影响 | 控制与退出标准 |
|---|---|---|---|
| R-001 | Boot4、SCA和第三方Starter冲突 | 高/高 | M0依赖树和最小集成；失败阻止扩展开发 |
| R-002 | 旧补丁有漏洞而新补丁未回归 | 中/高 | 双层版本表、SBOM、扫描、补丁回归；不直接上线原始基线 |
| R-003 | 买家tenant过滤漏在原生SQL/缓存/事件 | 中/极高 | 归属核对、隔离矩阵、全路径负向测试；任何成功越权阻断 |
| R-004 | 支付未知被当失败导致重复扣款 | 高/极高 | 单意图/唯一尝试、查单、关闭栅栏；故障测试必须通过 |
| R-005 | 退款与发货竞争 | 中/极高 | fulfillment本地冻结/发货互斥；并发实验与审计 |
| R-006 | 消息重复、乱序、回放产生重复效果 | 高/高 | Inbox、业务唯一键、墓碑、状态条件与长期保留 |
| R-007 | 对账和恢复只写文档 | 高/高 | 真实恢复报告作为v1退出条件，无证据不标完成 |
| R-008 | 服务过多导致个人项目烂尾 | 高/高 | 固定六业务域+identity，不并行实施第二认证框架；先垂直切片 |
| R-009 | 本机资源不足 | 中/中 | 按需启动、关闭全量观测、先测资源，不承诺16GB全部顺畅 |
| R-010 | 模拟支付与真实渠道差异 | 高/高 | 明确模拟边界；真实渠道另做验签、关单、退款、账单适配与审核 |
| R-011 | 多库恢复时间切面不同 | 中/高 | 隔离恢复、渠道核对、库存流水重建和差异处理 |
| R-012 | 控制台无鉴权/默认密码/配置泄密 | 中/极高 | 内网、默认凭据变更、Secret扫描、日志脱敏和密钥轮换 |
| R-013 | 发货事实可靠但出库消息未处理 | 中/高 | 监控差异、消费重试和对账；退款以fulfillment事实为准 |
| R-014 | 性能数字被误当已达标 | 高/中 | 所有数字标目标，报告携带环境与原始结果 |
| R-015 | 自建身份服务遗漏协议、密钥或退出语义 | 中/极高 | 复用框架；TC-027～030；持久化密钥、刷新撤销、JWT窗口明确，工期增加36～52h |
| R-016 | JPA隐式写入、N+1或批量更新绕过版本 | 中/高 | TC-031；显式SQL条件、真实MySQL并发、DTO投影、Flyway和OSIV关闭 |

个人项目风险责任人均为项目作者；进入团队项目时，为安全、资金、库存、平台分别指定负责人和备份，不能继续写“大家负责”。

## 3. 未决项与不阻塞项

| 项目 | 当前处理 | 必须解决的阶段 |
|---|---|---|
| 最终精确依赖、镜像tag/digest | 使用版本候选，不伪装联合验证 | M0 |
| identity精确依赖、Token受众、服务身份与认证持久化 | 自建方案已采纳；实现与配置冻结待最小链路证明 | M0/M1 |
| 前端与测试工具精确版本 | 按实现时官方资料核验 | 相应里程碑开始前 |
| MySQL UUID物理类型、索引与迁移DDL | 逻辑模型已定，物理实现待Explain和约束测试 | M1/M2 |
| 机器可读OpenAPI/事件Schema | 本次给设计清单，开工生成并加入校验 | M1前冻结首批，之后增量 |
| 是否公开部署演示 | 默认本地，未授权购买云资源或对外发布 | 如需发布再确定预算与访问方式 |
| 真实支付、税务、生产法律要求 | 不属于本次学习版承诺 | 单独生产立项 |
| 多仓、拆单、退货、预算/授信、合同价 | 明确延后，不偷塞通用框架 | 后续真实需求出现 |

## 4. 文档与变更审查

改业务范围，更新PRD和FR；改状态或金额口径，联动数据模型、契约、流程与测试；改依赖，更新版本证据和POC；改部署，更新恢复手册与风险。

每次新增服务或中间件必须回答：当前失败在哪里？现有组件为何不够？增加后由谁维护？如何验证删掉它反而不更好？不能用“企业级项目都这么做”作为理由。

## 5. 完整性的边界

本套文档覆盖产品定位、可验收需求、架构边界、逻辑数据、接口与事件、状态与补偿、安全租户、运维、测试、实施与风险，能够指导个人开始建设完整实战。

它不是已经实现的软件、最终详细设计、真实支付认证、生产容量证明或法律意见。正式编码仍需按阶段产出DDL、OpenAPI、事件Schema、运行配置、测试和证据；生产还需真实用户验证、容量成本评估、渠道资质与恢复/安全审查。

“详细完善”不等于一次写完后不再修改，而是每个关键假设都有边界、负责人、验证方法和可追踪的后续产物。
