# 14 骨架搭建与启动指南

更新：2026-10-20｜阶段：M0骨架已实现，完整兼容性POC尚未完成。

## 1. 当前交付

根Maven聚合工程包含八个独立可执行应用，统一JDK21、Boot4.0.8、Cloud2025.1.3、SCA2025.1.0.0。业务模块具有MVC、JPA、Flyway、MySQL驱动与Resource Server依赖；identity具有授权服务器依赖；Gateway使用WebFlux与OAuth2 Client，不依赖阻塞式MVC/JPA。

这些是架构入口和依赖骨架：没有业务Controller、实体、共享业务common包、假Token、默认账号，也没有已实现的OIDC登录。identity协议自动配置暂时明确排除，避免默认生成内存授权与启动时随机密钥。Gateway在完成OIDC客户端前拒绝业务请求，没有开放匿名代理。

| 模块 | 默认端口 | 包前缀 | 当前职责 |
|---|---|---|---|
| gateway | 8080 | com.cloudprocure.gateway | WebFlux入口与默认拒绝策略 |
| identity-service | 9000 | com.cloudprocure.identity | 自建认证服务入口，协议待实现 |
| access-service | 9101 | com.cloudprocure.access | 组织权限入口 |
| catalog-service | 9102 | com.cloudprocure.catalog | 商品入口 |
| trade-service | 9103 | com.cloudprocure.trade | 采购交易入口 |
| inventory-service | 9104 | com.cloudprocure.inventory | 库存入口 |
| payment-service | 9105 | com.cloudprocure.payment | 支付入口 |
| fulfillment-service | 9106 | com.cloudprocure.fulfillment | 履约入口 |

应用默认绑定127.0.0.1；容器环境如需监听其他地址必须显式配置SERVER_ADDRESS，不能直接据此对公网开放。

## 2. 构建与测试

根目录使用Wrapper（首次需要联网下载Maven与依赖）：

```powershell
# Windows PowerShell；Wrapper固定Maven3.9.9，要求JAVA_HOME为JDK21。
.\mvnw.cmd -B -ntp verify
```

Linux/macOS使用`sh ./mvnw -B -ntp verify`。根工程通过Maven Enforcer检查JDK21和Maven版本。IDE选择根pom.xml导入，Project SDK与Maven运行JDK均设21。

八个服务各有一个随机端口真实HTTP测试，验证健康状态UP、业务访问401、敏感管理端点拒绝；identity额外检查未配置发现端点不可用。测试不会连接MySQL、Redis或Nacos，不证明这些中间件已经兼容。测试报告位于各模块target/surefire-reports。

access另有一个JWT专项测试，以独立测试配置隔离基础设施、使用本机JWK公钥端点，验证真实资源服务的正常Token通过及签名/issuer/audience/过期异常拒绝，不使用Mock Decoder。本次共9项测试；测试公钥服务不是identity实现或OIDC协议测试。

## 3. 默认启动：skeleton

```powershell
# 单独启动网关；不需要Docker或中间件。
.\mvnw.cmd -pl gateway spring-boot:run

# 在另一个终端启动一个业务服务。
.\mvnw.cmd -pl services/access-service spring-boot:run

# 检查默认端口；只应看到最小健康信息。
Invoke-RestMethod http://127.0.0.1:8080/actuator/health
Invoke-RestMethod http://127.0.0.1:9101/actuator/health
```

也可构建后直接执行：

```powershell
# JAR为各模块独立可执行产物，不依赖先install其他服务。
java -jar services/identity-service/target/identity-service-0.1.0-SNAPSHOT.jar
```

不指定活动profile时默认skeleton。此模式禁用Nacos配置/发现、Sentinel与数据库自动装配；健康UP只表示应用进程及基础Web装配成功，不表示数据库、消息或认证就绪。profile不会创建H2假数据库，不应用于真实业务或生产。

## 4. 实际基础设施：local

Git仅跟踪各模块的`application-dev.yml`作为开发配置模板，`dev`可通过环境变量配置运行。本机使用时，将同目录的`application-dev.yml`复制为`application-local.yml`，在IDEA的Spring Boot运行配置中将Active profiles设为`local`。`application-local.yml`已被Git忽略，可填写个人连接参数；不要提交包含密码的运行配置。默认`skeleton`保持不变。

本机`application-local.yml`的Nacos配置与发现地址均使用`127.0.0.1:8848`，对应Docker Compose映射到Windows宿主机的端口。其他配置仍需填写或通过该Java进程的环境变量提供；Compose的`deploy/.env`不会自动传给IDEA启动的Java进程。新复制模板时，可将两处`${NACOS_SERVER_ADDR}`替换为该地址。

local使用必需的Nacos Data ID导入和真实MySQL参数，缺少配置就失败；它不是为了脱离环境而启动成功的降级模式。中间件启动与账号准备见[deploy说明](../deploy/README.md)。

所有模块的dev配置所需：NACOS_SERVER_ADDR、NACOS_NAMESPACE（命名空间ID）、NACOS_USERNAME、NACOS_PASSWORD；local已填入的值无需再提供对应环境变量。Nacos中需存在对应应用名的`.yaml`配置，DEFAULT_GROUP。不把密码放入Data ID或提交到Git。

各持久化服务还需独立环境变量：

| 服务 | URL | 账号 | 密码 |
|---|---|---|---|
| identity | IDENTITY_DB_URL | IDENTITY_DB_USERNAME | IDENTITY_DB_PASSWORD |
| access | ACCESS_DB_URL | ACCESS_DB_USERNAME | ACCESS_DB_PASSWORD |
| catalog | CATALOG_DB_URL | CATALOG_DB_USERNAME | CATALOG_DB_PASSWORD |
| trade | TRADE_DB_URL | TRADE_DB_USERNAME | TRADE_DB_PASSWORD |
| inventory | INVENTORY_DB_URL | INVENTORY_DB_USERNAME | INVENTORY_DB_PASSWORD |
| payment | PAYMENT_DB_URL | PAYMENT_DB_USERNAME | PAYMENT_DB_PASSWORD |
| fulfillment | FULFILLMENT_DB_URL | FULFILLMENT_DB_USERNAME | FULFILLMENT_DB_PASSWORD |

URL例如`jdbc:mysql://127.0.0.1:3306/access_db?serverTimezone=UTC`。使用自己的库与账号；开发连接是否需要TLS及驱动参数按实际服务器配置决定，不默认关闭TLS或放宽公钥获取。

六个业务服务额外需要OIDC_ISSUER_URI和OIDC_JWK_SET_URI，并校验`cloudprocure-api`受众；issuer和JWKS均必须来自真实的自建认证环境。当前identity还未实现签发能力，因此local模式不构成完整登录闭环。租户与资源授权也尚未实现，不能因JWT校验成功便视为业务鉴权完成。

在IDE运行配置或当前终端设置这些变量后启动：

```powershell
# 仅在上述必需变量和真实依赖准备完成后运行。
$env:SPRING_PROFILES_ACTIVE = 'local'
.\mvnw.cmd -pl services/access-service spring-boot:run
```

Gateway与identity的local模式仍保持业务拒绝，后续认证里程碑将替换为真实协议/客户端配置。Sentinel依赖已装配，但规则治理尚未接入，因此显式禁用；RocketMQ尚未加入运行依赖，避免在没有消息用例时伪造消息集成。

## 5. 继续实现的顺序

先完成identity的账号、框架JDBC授权仓储、持久化签名密钥和Code+PKCE；随后接通Gateway的OIDC客户端与服务端会话，再验证一条受保护API。服务身份mTLS、撤权、MFA和恢复按各自验收用例继续，不能把本次骨架测试当作完成这些要求。

业务用例到来时才创建实体、迁移和分层包；库存条件更新及Outbox等非平凡逻辑需要对应测试。当前不生成空的领域接口和通用响应框架，也不提前创建前端或云部署配置。
